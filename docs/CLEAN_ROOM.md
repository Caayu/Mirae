# Clean-room policy

Tela aims at professional painting behaviour comparable to established
illustration applications. It is developed **clean-room**: behaviour may be
studied from the outside; the implementation is original.

## Allowed

- Observing the **behaviour** of other applications as a user would: what
  a stroke looks like, how a control responds, timing, ranges. Comparative
  tests must evaluate behaviour (outputs, measurements), never internal
  structure.
- Public mathematics and literature: papers, textbooks, standards and
  public specifications (e.g. Porter & Duff 1984 compositing,
  Fritsch–Carlson 1980 monotone interpolation, Casiez et al. 2012 One Euro
  filter, Yuksel et al. 2011 centripetal Catmull–Rom, W3C Compositing and
  Blending for future blend modes, public OS/API documentation such as
  Windows Ink).
- Open-source libraries used as dependencies under their licenses
  (listed in docs/architecture/crate-dependencies.md).
- Our own measurements, benchmarks and design reasoning.

## Not allowed

- Copying or adapting code from proprietary software, including
  decompiled code, decompiler pseudocode, disassembly or third-party
  assembly.
- Using decompiled or reverse-engineered **algorithms** as the basis of an
  implementation.
- Proprietary assets: images, icons, brush tips, textures, sounds, fonts.
- Proprietary shaders, extracted or reconstructed.
- Proprietary presets, brush settings or their values, extracted from
  application data.
- Undocumented proprietary file formats or internal schemas (database
  layouts, setting names, internal identifiers) as a basis for Tela's
  formats or names.

## How the project complies

- Every brush tip image and paper texture is **generated by code**
  (`tip/image.rs`, `texture.rs`); there are no image assets.
- The 8 built-in presets were designed from scratch for Tela, with Tela's
  own parameters and ids (`tela.*`).
- The preset format is Tela's own (ADR 0008).
- Algorithms are documented with their public sources or derivations in
  code comments, phase reports and ADRs.
- An earlier, separate analysis of a commercial application's binaries
  exists in the developer's history (outside this repository). Nothing from
  it — schema, names, values, code, assets — may be used in Tela. Do not
  consult or import it when working on Tela.

## Black-box comparison

Tela's parity reference is Clip Studio Paint ([PARITY.md](PARITY.md)).
Comparisons with it are behavioural only:

- **Allowed:** running the application and operating its UI as a user
  (including automated mouse/keyboard/pen input), screen captures and
  measurements of what it displays, files it exports through its normal
  UI in open formats (PNG), timing measured from the outside, its public
  user documentation.
- **Not allowed:** reading its executable, libraries, memory or traffic;
  opening its installation or user-data files (presets, brushes,
  materials, settings, databases); using its proprietary file formats as
  a source; reusing the earlier binary analysis mentioned above.
- Each comparison is recorded with version, environment, steps,
  observation and Tela's result in `docs/parity/`. Tela's implementation
  of an observed behaviour is derived from that description, public
  mathematics and our own reasoning.

## When in doubt

Describe the desired behaviour in your own words, derive the math from
public sources, write a behavioural test, implement. If a source's license
or provenance is unclear, do not use it, and ask.
